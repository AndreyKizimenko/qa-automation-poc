# Linux software fixtures

Two real upstream installers kept under their upstream filenames —
`step-cli_0.30.2-1_amd64.deb` (`premium/software/library.spec.ts`) and
`sublime-text_build-4200_amd64.deb` (`premium/software/edit-package.spec.ts`) —
and three inert packages generated by `make-deb.py`, below.

## `fleet-playwright-install_1.0.0_all.deb`

The Ubuntu VM's durable install/uninstall fixture, declared in
`gitops/premium-fleetqa/fleets/vms.yml` and used by
`premium/software/software-lifecycle-on-host.spec.ts`. One marker file under
`/usr/share/fleet-playwright-install/`, no maintainer scripts, `Architecture:
all` so a VM of either architecture installs it. Rebuild with
`python3 test-data/linux/software/make-deb.py fleet-playwright-install 1.0.0 all`
(sha256 `6fcc33be969fa089a58ab69e4a3749c96f2b642704c6ec176c92105582c9dcc3`).

## `fleet-playwright-pkg_1.0.0_amd64.deb`

An inert 662-byte Debian package: one marker file under
`/usr/share/fleet-playwright-pkg/`, no maintainer scripts, nothing that touches
a host. Used by `premium/software/package-scripts.spec.ts`.

It exists because a spec needs a package whose **title name is unique across
the suite**. Fleet names a `.deb` title after the `Package:` field, so every
real `.deb` here shares a title with another spec's fixture ("step-cli",
"Sublime Text"), and a premium title can hold several packages — two specs
uploading to the same title on the same fleet leaves the Library accordion with
two rows and every row-scoped locator ambiguous. `Package: fleet-playwright-pkg`
belongs to one spec and always will.

A `.deb` in particular, rather than a tarball or a script package, because Fleet
generates *both* an install and an uninstall script for it, and both are short
enough for Ace to render whole — Ace virtualises long documents, so a real
installer's scripts would only be partly in the DOM and could never be compared
against what the API stored.

### Regenerating

```sh
python3 test-data/linux/software/make-deb.py
```

Standard library only, and deterministic: file mtimes are pinned to the epoch,
so a rebuild is byte-identical (sha256
`bf7b4fba7b20f287644e9ab5f37d6b510fce974c3bb4e044555beb110931a6d5`).

The script writes the `ar` archive itself instead of shelling out to `ar`.
macOS's `ar` always prepends a `__.SYMDEF` member, and Fleet detects a `.deb`
by the magic bytes `!<arch>\ndebian` — the `debian-binary` member has to come
first or the upload is rejected as an unsupported file type.

## No `.rpm` on disk

The suite's `.rpm` is built in memory, per test, by `helpers/rpm.ts`
(`inertRpm(name, version)`), and its tarball by `helpers/tarball.ts`. Fleet
names an `.rpm`'s title after the package's `Name`, and a fleet holds one
installer per title, so a file kept here could serve one test at a time: the
per-OS smokes (`premium/matrix/os-smokes.spec.ts`) install on the lab's five
rpm hosts side by side, on one fleet, and each needs a package of its own name.
`helpers/deb.ts` exists for the same reason.

What the built `.rpm` is, and why it is safe on a real host: `noarch`, one
marker file under `/usr/share/<name>/` and that directory itself, no scriptlets,
no dependencies, unsigned. Listing the directory is what makes `rpm -e` (which
`dnf remove` and `zypper remove` end in) remove it with the package, so an
install and an uninstall leave the host as it was. The helper's header has the
format and the rpm versions it was checked on. To look at one, from
`playwright/`:

```sh
node -e "require('fs').writeFileSync('look.rpm', require('./helpers/rpm.ts').inertRpm('fleet-pw-look', '1.0.0'))"
rpm -K -v look.rpm && rpm -qpl look.rpm      # on any rpm-based system, or in its container
```

The tarball holds one `marker.txt` and runs nothing: a `.tar.gz` package is
whatever its install and uninstall scripts do, and those are the test's.
