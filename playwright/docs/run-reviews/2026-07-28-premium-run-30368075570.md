## 1. `Software Titles — vulnerable filter…` — product-defect (new)

### Evidence

Failing assertion, all 3 attempts identical:

```
Locator:  getByRole('table').locator('tbody tr').nth(27).locator('td').nth(3)
Expected: not "---"
Received: "---"
   at helpers/vuln.ts:29
```

Row 27 is not a rendering artifact. From the retry-1 trace's network entry for the
list the page actually loaded —
`GET /api/latest/fleet/software/titles?page=0&per_page=50&order_direction=desc&order_key=hosts_count&vulnerable=true&exploit=false&fleet_id=0`
(200, 50 titles of 252) — index 27 is:

```json
{ "id": 11083, "name": "fuse3", "source": "deb_packages",
  "hosts_count": 100, "versions_count": 2,
  "versions": [ { "id": 11471,  "version": "3.10.5-1build1",   "vulnerabilities": null },
                { "id": 155208, "version": "3.10.5-1build1.1", "vulnerabilities": null } ] }
```

Every other row on the page carries ≥1 CVE. So the UI was **right** to print `---`:
the payload it got has no vulnerabilities for either version. The fault is that the
API returned this title at all under `vulnerable=true`.

Live probes confirm the scope mismatch:

```
GET /software/titles/11083            (all fleets)  → 3 versions, hosts 101
  11471  3.10.5-1build1     hosts 99  cves —
  155208 3.10.5-1build1.1   hosts 1   cves —
  156311 3.18.2-1           hosts 1   cves CVE-2026-33150, CVE-2026-33179   ← the only vulnerable one

GET /software/titles/11083?fleet_id=0 (Unassigned) → 2 versions, hosts 100 (156311 absent)

GET /hosts?software_version_id=156311 → host 415 ubuntu-prem-QEMU-Virtual-Machine, team_id 103 "VMs"
```

The single vulnerable version lives on a host in fleet **VMs**, yet the title is
returned for `fleet_id=0`.

### Root cause (Fleet source)

`server/datastore/mysql/software_titles.go` scopes the two halves of the response
differently:

- the `vulnerable=true` filter (~L743-750) joins
  `INNER JOIN software s ON s.title_id = st.id INNER JOIN software_cve scve ON s.id = scve.software_id`
  — **no team predicate at all**; any CVE on any version of the title, in any fleet,
  qualifies it.
- the per-version payload (`selectSoftwareVersionsSQL`, ~L1218) reaches CVEs through
  `software_host_counts` gated on the requested scope
  (`shc.team_id = 0 AND shc.global_stats = 0` for `fleet_id=0`), so out-of-scope
  versions — and their CVEs — are excluded.

Host scoping for the title itself comes from `software_titles_host_counts`, which
`fuse3` satisfies (100 Unassigned hosts on non-vulnerable versions). Filter says
"vulnerable", payload says "nothing here".

The unscoped join predates 1c7d2a0 (2025-06-07), so this is **latent, not a 4.90
regression**. It surfaced now only because instance data changed: host 415 in fleet
`VMs` picked up `fuse3 3.18.2-1`.

### Draft Fleet bug (review before filing — not filed)

> **Title:** Software titles `vulnerable=true` filter is not fleet-scoped — rows show `---` in the Vulnerabilities column
>
> **Fleet version:** 4.90.0-rc (premium). Latent since at least 2025-06.
>
> **Steps to reproduce**
> 1. Have a software title installed on hosts in two fleets, where only the version in fleet B has a CVE (here: `fuse3`, vulnerable `3.18.2-1` on a host in fleet `VMs`, non-vulnerable `3.10.5-*` on 100 Unassigned hosts).
> 2. Go to **Software → Inventory**, scope **Unassigned**, apply the **Vulnerable** filter.
> 3. Find `fuse3` in the list.
>
> **Expected:** `fuse3` is not listed — it has no detected vulnerabilities in the Unassigned scope. (Or, if a global filter is intended, the Vulnerabilities column shows the CVEs rather than `---`.)
>
> **Actual:** `fuse3` is listed with `---` in the Vulnerabilities column: a row with no vulnerabilities inside a list filtered to vulnerable software.
>
> **API evidence**
> ```
> GET /api/latest/fleet/software/titles?vulnerable=true&fleet_id=0   → includes fuse3 (id 11083)
> GET /api/latest/fleet/software/titles/11083?fleet_id=0             → 2 versions, both "vulnerabilities": null
> GET /api/latest/fleet/software/titles/11083                        → 3rd version 3.18.2-1 carries CVE-2026-33150, CVE-2026-33179
> GET /api/latest/fleet/hosts?software_version_id=156311             → host 415, team_id 103 ("VMs")
> ```
>
> **Suspected cause:** in `server/datastore/mysql/software_titles.go`, the `vulnerable=true` join (`software` → `software_cve` on `s.title_id = st.id`) carries no team predicate, while `selectSoftwareVersionsSQL` resolves version CVEs through scope-gated `software_host_counts`. The filter and the payload disagree about scope.

An alternative reading is that the filter is *meant* to be global ("this title is
known vulnerable somewhere"). Even under that reading the UI is wrong to render
`---`, so the fix is Fleet's either way — that's why this is product-defect and not
test-bug. Confidence in "Fleet owns it": high; in "the filter should be scoped":
medium.

## 3. `host expiry cannot be opted out of when it is enabled globally` — test-bug

### Evidence

```
Locator: getByRole('checkbox', { name: 'enableHostExpiry' })
Expected: "true"   Received: "false"
resolved to <div role="checkbox" aria-checked="false" aria-readonly="false" aria-disabled="false" …>
```

Note `aria-disabled="false"` as well — the checkbox is unchecked *and* editable,
which is exactly Fleet's correct rendering when host expiry is **not** enabled
globally.

The spec's own header comment states the opposite premise:

> The host-expiry assertions depend on host expiry being enabled globally, which
> it is on both QA instances (`host_expiry` = 1 day, …)

That premise is false, and the repo contradicts it:

- `GET /api/latest/fleet/config` in the run's trace, and live now:
  `{"host_expiry_enabled": false, "host_expiry_window": 0}`
- gitops sets it false on **all four** QA envs —
  `gitops/premium-fleetqa/default.yml:11`, `premium-fleetqa-min/default.yml:11`,
  `free-fleetqa/default.yml:11`, `free-fleetqa-min/default.yml:11`.
- [advanced-options.spec.ts:16](../../tests/e2e/premium/settings/advanced-options.spec.ts#L16)
  documents that the suite deliberately leaves `host_expiry_settings` alone:
  "raising or lowering that window can make Fleet delete hosts, which the whole
  host-dependent batch relies on."

The test is new (7a219c2, 2026-07-27, Batch 4) and has never passed — it also failed
in the preceding dispatch (run 30365894788). Product behaviour is correct; the test
asserts an inherited-on state that no QA instance is in.

### Suite next step

Hand to `playwright-test-author`. Do **not** enable global host expiry to make this
green — gitops would revert it and a live expiry window risks deleting the
osquery-perf hosts the rest of the suite depends on. Two viable rewrites:

1. **Assert the state that actually exists** — global host expiry off ⇒ the fleet
   checkbox is unchecked, `aria-disabled="false"`, no inherit help text, and the
   tooltip still explains the setting. Keeps the tooltip/help-text coverage, drops
   the unreachable inherit assertion.
2. **Establish the precondition in-test** — PATCH `/config` with
   `host_expiry_enabled: true` and a deliberately huge `host_expiry_window`
   (e.g. 3650 days, so nothing is swept), snapshot/restore in `finally`. Riskier:
   it mutates *global* config on a shared instance while other specs read it, so it
   would need serialization against the rest of the settings area.

Option 1 is the recommendation — cheaper and it doesn't put host deletion one typo
away.

## 4. macOS + Windows titles→CVE variants skip every run — test-bug

Reported as skips, so easy to miss, but these are not environment-driven:

```
premium | vulnerabilities.spec.ts | macOS — software titles → version → CVE detail flow    (skipped)
premium | vulnerabilities.spec.ts | Windows — software titles → version → CVE detail flow  (skipped)
```

The gate is `test.skip(!softwareByOS[osKey], 'No <platform> software found')`, fed by
`findVulnerableSoftwareBySource`, which fetched a **single page** (`per_page=100`, no
`page` loop) and took the first source match.

Live: 262 vulnerable titles exist, of which **82 `apps` (macOS) and 23 `programs`
(Windows)** — but page 0 is `deb_packages: 96, vscode_extensions: 4`, so neither
platform could ever match. The macOS/Windows *host*-path variants in the same spec run
fine, which is what made the skip look plausible.

Two further problems surfaced while fixing it, both worse than the paging bug:

**The helper swallowed API failures as "no such software".** `if (!res.ok) return
null` is indistinguishable from "the instance has no macOS software", and the caller
turns `null` into a skip. So any failed lookup silently deleted a platform's coverage.

**The QA instance's MySQL cannot serve these queries under worker concurrency.** With
paging in place the lookup failed outright, and once the helper was made to throw, the
cause was visible:

```
[findVulnerableSoftwareBySource] apps page 0: 500
  Error 1114 (HY000): The table '/tmp/#sql1_d1cef_21b' is full
```

`vulnerable=true` on `/software/titles` builds a large temp table, and the spec fired
one such query **per platform per worker** in `beforeAll` (4 workers × 3 groups). The
same query runs fine sequentially — a standalone paged sweep of all three groups
succeeds every time — so this is instance capacity, not a query bug: **infra-env**.
It is very likely a hidden contributor to unexplained flakiness elsewhere (the
preceding run's 8 flaky tests are a candidate), because a 500 on a vuln query trips
the `pageHealth` fixture.

Worth raising with whoever owns the QA instance: `tmp_table_size` /
`max_heap_table_size` / `tmpdir` capacity on the premium QA MySQL.

Fixes applied (all verified green, see below):

- One paged sweep resolves every platform group instead of one sweep per group —
  cutting the concurrent heavy queries by 3× and removing the failure in practice.
- A non-OK response now throws with status and body instead of resolving to `null`, so
  an API or instance fault can never again masquerade as missing test data.
- A match must carry a CVE on a version returned **for the requested scope**, so the
  drill-down can't land on a #50059 leak and fail for the wrong reason.
- The lookup is scoped with `fleet_id=0`, matching where the spec then navigates
  (previously it picked from the all-fleets scope).

A related silent-null remains in `findHostByPlatform`, which `continue`s past a failed
per-host software probe and returns `null` — the same class of hidden skip. Not
touched here; worth the same treatment.
