## Reasoning — why "suspected", and the fault line

Two readings, both pointing at a real gap but with different owners:

1. **Product-defect.** Fleet's vuln-matching layer associates CVE-2026-61898 with
   an installed package and the UI renders it as a clickable link, yet the
   CVE-detail service disowns it ("no source is aware"). A user clicking that link
   hits a dead "Vulnerability not detected" page. Surfacing a clickable CVE whose
   own detail endpoint 404s is a UX/data-consistency defect regardless of cause.

2. **QA-instance data artifact / enrichment lag.** CVE-2026-61897/61898 look
   injected or newly-ingested: sequential ids, identical creation timestamp, no
   CVSS, and *every* Fleet source reports them unknown while still being matched to
   a package. If they're synthetic seed CVEs (or matched before metadata
   enrichment ran), the detail endpoint is arguably behaving correctly and the
   **test** is at fault for assuming any reachable CVE has a working detail page.

The determining question — *are CVE-2026-61897/61898 real CVEs Fleet should
resolve, or QA seed artifacts?* — is for a human to confirm (they postdate the
Jan-2026 knowledge cutoff, so I can't check NVD). Either way the immediate,
high-confidence action is the same test-hardening; the Fleet bug is for the
underlying "matched-but-unknown CVE → clickable → 404" inconsistency.

## Root cause — CONFIRMED Fleet product bug (source-traced 2026-07-24)

Investigated with instance creds + the Fleet source. The verdict is no longer
"suspected" — this is a genuine backend inconsistency, and the QA CVEs merely
land the suite in the state that exposes it.

**The contradiction, proven at the API:**
- `GET /api/latest/fleet/vulnerabilities?query=CVE-2026-61898` → **200**, `hosts_count: 2`, `counts_updated_at` ~17 min old. Fleet lists it as a live vuln on 2 hosts.
- `GET /api/latest/fleet/vulnerabilities/CVE-2026-61898` → **404** "This is not a known CVE. None of Fleet's vulnerability sources are aware of this CVE." (both team scopes)

**Why the two endpoints disagree — three tables:**
- `software_cve` — the match table. **Has** CVE-2026-6189{7,8} (matched to `accountsservice` on the deb host).
- `vulnerability_host_counts` — per-CVE host rollup. **Has** a global row, `host_count = 2`.
- `cve_meta` — NVD metadata (CVSS/EPSS/published/description). **Missing** these CVEs (they're brand-new, unpublished → never synced; that's why severity/published render "---").

**The code paths (fleet @ current checkout):**
- List → [`buildListVulnerabilitiesSQL`](../../../../fleet/server/datastore/mysql/vulnerabilities.go) (`server/datastore/mysql/vulnerabilities.go:334-344`): `FROM vulnerability_host_counts vhc WHERE host_count > 0 AND EXISTS(software_cve …)`. `cve_meta` is `LEFT JOIN`ed *only* when sorting/filtering by a metadata column → **metadata optional**. CVE appears.
- Detail (premium) → EE override forces `useCVSScores=true` (`ee/server/service/vulnerabilities.go:26`), selecting `eeSelectStmt` in `Datastore.Vulnerability` (`server/datastore/mysql/vulnerabilities.go:34-46`): `FROM cve_meta cm JOIN (software_cve UNION operating_system_vulnerabilities) …` — **inner join on `cve_meta`**. No metadata row → 0 rows → `sql.ErrNoRows` → NotFound.
- Fallback → `Service.Vulnerability` (`server/service/vulnerabilities.go:204-214`) then calls `IsCVEKnownToFleet`, which is literally `SELECT 1 FROM cve_meta WHERE cve = ?` (`server/datastore/mysql/vulnerabilities.go:870-877`). Also empty → `known=false` → `cveNotFoundError{}` → **HTTP 404**.

**Why it's a defect, not seed noise:** whenever a CVE is matched to host software but has no `cve_meta` yet — a normal, real state for very recently-published or distro-sourced CVEs where the NVD sync lags matching — Fleet lists it (with host counts and a clickable link) but its detail page 404s with a message asserting no Fleet source knows it, when the matcher plainly does. The list treats `cve_meta` as optional; the detail requires it. A user hits exactly the dead end our test hit. (Note the endpoint already has a "known but unmatched" branch returning 204 at `server/service/vulnerabilities.go:156` — the inverse quadrant — so "matched but unenriched" 404ing is an unhandled gap, not intended.)

**Suggested Fleet fix direction (for the issue, not prescriptive):** the detail
lookup should surface matched-but-unenriched CVEs the way the list does — treat
`cve_meta` as optional (LEFT JOIN) and derive existence/`known` from
`software_cve`/`operating_system_vulnerabilities`, rendering null metadata rather
than 404ing. At minimum, stop returning "no source is aware" for a CVE that has
software/OS matches.

**Test angle (secondary now):** the test correctly caught a real bug. It will
stay red nightly until Fleet fixes it or the QA CVEs enrich. If we want the
nightly green to keep catching *other* regressions, harden the flow to skip CVEs
whose detail endpoint 404s — but do it with an inline comment linking the filed
Fleet issue, so it's tracked, not silently hidden. Hand to `playwright-test-author`.
