# 4.93 RC loadtest — first pass, 2026-10-01

**Instance:** `fleet-493loadtest.loadtest.fleetdm.com`, 4.93.0-rc (`rc-minor-fleet-v4.93.0`), fleet 1 "Ducks":
100,000 hosts (60k macOS / 20k Windows / 20k Ubuntu, all offline during the run), 505k software titles,
817k versions, 47k CVEs, 530 labels, 500 policies, 500 reports, 48 scripts, 260 installers, 1,424
Fleet-maintained apps. MDM off. The instance was otherwise idle, so every number below is a floor:
under agent load the same requests were 2–10× slower in the morning probe (labels with host counts
37–48 s, `os_versions` 50 s, hosts list 18–39 s).

**Budget:** 5 s per request and per page. **Methods:**
- API matrix, P0 shapes, 3 samples each, one request in flight (`npm run test:loadtest:api`,
  `.perf-history-api/2026-10-01_151344/`).
- Page-load suite, headless, one worker (`npm run test:loadtest`, `.perf-history/2026-10-01_152721/`).
- A page drive that loads each page the way a user reaches it and records the exact requests the UI
  sends, then re-times those exact shapes 3× with curl. The "server" column below is that median; "page"
  is the time until the page stopped making API calls, minus the 4 s settle window.

## B. Slow or broken only through the API, fleetctl or integrations

Lower priority: no page sends these shapes, so they hit customers who script against the API, use
`fleetctl get`, or sort/filter through an integration.

| Request | Server | Why the UI doesn't hit it | Issue |
|---|---|---|---|
| `os_versions` with the API default (no `order_key`, no `max_vulnerabilities`) | **14–17 s**; `platform=linux` **19 s** | the OS page and the dashboard card send `order_key=hosts_count` and `max_vulnerabilities=3` / `0`, which take 0.3–1.5 s | new — the default plan is the slow one |
| `vulnerabilities?order_key=created_at&order_direction=desc` (the documented default, sent explicitly) | **27 s** (0.6 s when omitted) | the page sorts by `hosts_count` | new — same query, different plan |

| `labels` with the default `include_host_counts=true` | 4.6 s idle, **37–48 s** under load | the UI sends `include_host_counts=false` | fleetdm/fleet#4890 (closed 2022, regressed) |
| `hosts?connected_to_fleet=true&fleet_id=N` and `hosts/count` with the same | **422** every time (200 without `fleet_id`) | no UI control for this filter | new |
| `hosts/count?order_key=issues` | **422** (other keys 200) | the UI never sorts the count | low — `issues` isn't a hosts-table column |
| `software/versions` with the API default (vulnerability details on) | 0.3 s here; **8–9 s** on a 19-host instance with 12k CVEs | the page sends `without_vulnerability_details=true` | watch — #45415 path, scales with CVEs not hosts |

Documentation mismatches found on the way, not performance: the REST docs list
`mdm_enrollment_status=manual-personal` but the server accepts `personal` (fleetdm/fleet#52285 /
#53677 are reworking that status); `exclude_fleet_maintained_apps` is documented for
`software/titles` but nothing decodes it; the four CVE sort keys for `software/versions` are only
accepted while vulnerability details are included, which the docs don't say.

## C. Not measurable on this run

- MDM is off, so OS updates, Configuration profiles, OS settings status links, Certificates (Android
  MDM) and `commands` render "Additional configuration required" or answer 400. Both suites skip them
  with that reason now; they are the fleetdm/fleet#48996 and #42565 shapes and need the MDM-on run.
- No finished batch script run existed, so the batch-progress host-results shapes were skipped.
- Hosts were offline, so `status=online` views were empty (and fast).

## D. Where the data is and how to repeat

- API pass: `npm run test:loadtest:api` (P0 only: `API_PRIORITY=P0`; more samples: `API_SAMPLES=10`);
  results and the comparison table land in `.perf-history-api/<timestamp>/`.
- Page loads: `npm run test:loadtest` (one worker; needs the admin password in `.env.loadtest`).
- Exact UI shapes: the `ui` family in `tests/loadtest/api/shapes.ts` is the page drive's request list
  verbatim (`npm run test:loadtest:api -- -g ui`), so the next pass times what users see without
  driving a browser; the page drive script itself is a one-off kept out of the repo.
- Issue search for duplicates was done on 2026-10-01; "new" above means no open or closed issue
  matched the endpoint and symptom.
